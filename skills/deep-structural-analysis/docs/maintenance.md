# 维护流程（maintenance）

> 本文件是 skill 项目的维护契约——升级 skill 时必须遵守。
> 与 UPDATELOG 的分工：UPDATELOG 记录"变更了什么"；本文件规定"怎么改"。

## 一、升版必答（每次升级必须回答）

1. **新增/淘汰了哪些机制**——机制淘汰评估（连续 5 次实战未触发 → 淘汰评估）
2. **文档同步检查**：改动的机制是否同步了所有相关位置？
   - SKILL.md 主章节 ↔ 机制执行分层协议 ↔ Gotchas ↔ Invocation Protocol
   - references/checklist.md 对应检查项
   - 跨 skill 同步：**共享纪律（置信度/验证分级/攻击循环/立场征集/边界协议/机制淘汰）在两个 skill 中各自内联——改动必须双处同步**（自包含的代价，用流程管理）
3. **词数预算核对**（见下）
4. **slop 审计**（见下）
5. **Plan 自审**（竞争性假说/二阶效应/物理锚定/博弈完整性/前提验证）

## 二、词数预算

> 预算防机制膨胀（v1.9.0 教训：40+ 机制超出执行容量）。超标 → 先精简表述；无冗余可删 → 按机制淘汰条款评估。

| 文件 | 预算 |
|---|---|
| SKILL.md | ≤ 500 行（Claude 官方规范） |
| SKILL.md 各章节 | 不设独立预算——以总行数为闸门 |
| docs/maintenance.md | ≤ 300 行 |
| docs/decisions/README.md | 每条决策 ≤ 40 行 |

## 三、slop 审计清单（升级时对改动区域检查）

- [ ] **重复规则**：同一规则是否在多个位置定义？（one home per fact——保留一个权威，其余链接）
- [ ] **历史叙述**：正文是否出现"之前/现在/已改名/后来"类变更叙述？（当前状态进正文，变更故事进 UPDATELOG/decisions）
- [ ] **实施状态标注**："已实现/未来将…"类标注？（状态会腐烂——删除）
- [ ] **推理过程**：正文是否混入"为什么这样设计"的推导？（契约进正文，推导进 decisions/）
- [ ] **强调膨胀**：加粗/大写是否到处都是？（保留关键强调，删除次要）
- [ ] **段落墙**：一段承载多条规则的？（拆分或降级）

## 四、跨 skill 共享纪律清单（改动需双处同步）

以下纪律在两个 skill 中各自内联（自包含设计——每个 skill 必须独立可加载）：

1. 置信度判定标准（高/中/低）
2. 验证强度分级（公开验证/公告声明/归因声明）
3. 攻击循环协议（暴露靶子/邀请真实攻击/修订痕迹/承认局限）
4. 立场征集（向用户征集立场/视角审计降级/模拟深度标注）
5. 边界协议（禁止"我执行了 X"句式）
6. 机制淘汰与升版必答
7. 收敛协议（已确认/未确认/待验证信号/分析边界）

> 修改任一共享纪律：两个 SKILL.md 必须同步更新，并在各自 UPDATELOG 记录。

## 五、与 DSH 文档工程化的对应

| DSH 机制 | 本项目对应 |
|---|---|
| one home per fact | slop 审计第 1 条 + 共享纪律清单 |
| 词数预算（verify-doc-budgets） | 第二节预算表 |
| slop checklist（dsh-doc-standards） | 第三节清单 |
| Agent Notes（决策记录） | docs/decisions/ |
| cookbook | docs/cookbook/ |
| 文档与代码强绑定 | 升版必答第 2 条（文档同步检查） |
